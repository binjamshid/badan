GUIDELINE 2.1 — CLINICAL HEALTH RECORDS

Integration, upload location and frequency:
It is never uploaded and never leaves the device. BADAN requests read-only access to ONE clinical type — HKClinicalTypeIdentifier.labResultRecord — via requestAuthorization(toShare: [], read: [labResultRecord]). The empty share set means we never write to or modify Apple Health. No other clinical type is requested (not medications, conditions, immunizations, procedures, allergies or vitals). On that tap we run one HKSampleQuery, parse the FHIR on device, and write to local storage. There is no upload step, so no frequency. This code path contains no networking API and constructs no URL.

What requires it; enabling and disabling:
One feature: the Lab notebook, keeping lab results alongside a person's own health data. Enabled only by an explicit tap: Log > Lab notebook > "Import from Health". That tap is the app's only caller of the clinical-records API: no background delivery, no observer, no scheduled task, no import at launch or on sync. A user who never opens that screen never triggers a clinical read.
Turned off two independent ways: revoke access in iOS Settings > Privacy & Security > Health > BADAN, or in-app delete results individually or turn off "Sensitive records", which permanently deletes the entire encrypted database they live in.

How else it is utilized:
It is not. Results appear in the Lab notebook and nowhere else. They are never sent to our optional AI coach — the component assembling coach context cannot bind to the database they live in, and an automated test asserts sensitive records cannot appear there. They are never in a default export, never used to compute a score, and never used for analytics (there is no analytics SDK). Imported values keep the provider's reference range and abnormal flag; BADAN adds no interpretation.

Where it is stored, who has access:
On device only, in badan_sensitive.db — a separate SQLite database encrypted with SQLCipher, keyed from the Keychain with kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly, so the key never leaves the device and is not in backups. Only the person using the device has access. There is no account, login, sync or server-side copy; the developer has no means of accessing a user's lab results.

Three optional, off-by-default features reach the network; none can access that database or any health record: the AI coach (sends a question the user typed), export delivery to a user-entered address, and methodology feedback, new in build 5 and declared here rather than left to be found. It is off unless enabled, and only offered after the user has used the "does this match how you felt?" option. It sends which metric and method the user disagreed with, whether they felt better or worse, roughly how often as a range ("10-19"), and whether we had adjusted that number — never a reading, magnitude, date, location, or any identifier of user or device. Nothing sends below ten answers; submission is at a random point 24-72h later. Users can read every submission verbatim in Settings. Our App Privacy declaration is now Other Usage Data, not linked, not used for tracking.

## Notes to include in App Review Information for future submissions

BADAN reads HealthKit Clinical Records (lab results only, read-only) exclusively when the user taps
"Import from Health" in Log → Lab notebook. Records are parsed on device and stored in a
SQLCipher-encrypted local database. They are never uploaded, never sent to the app's optional AI
coach, never included in a default export, and never used to compute a score. The app has no
account system and no server-side storage of health data.
