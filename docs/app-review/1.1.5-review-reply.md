Thank you for the review. Both items are addressed below, and build 1.1 (5) contains the fix for
Guideline 3.1.2(c).

## Guideline 2.1 — Clinical Health Records API integration

**Summary: BADAN reads lab results from HealthKit Clinical Records only when the user taps a
button, stores them in an encrypted database on the device, and never uploads them anywhere.
There is no server-side copy, no account, and no automatic or background access.**

**How the app integrates with the Clinical Health Records API. Where is the information uploaded?
At what frequency?**

The information is not uploaded anywhere. It never leaves the device.

BADAN requests read-only authorization for a single clinical type,
`HKClinicalTypeIdentifier.labResultRecord`, via
`HKHealthStore.requestAuthorization(toShare: [], read: [labResultRecord])`. The share set is empty:
the app never writes to Apple Health and never modifies a clinical record. Nothing else in the
clinical family — medications, conditions, immunizations, procedures, allergies, vitals — is
requested.

When the user taps "Import", the app runs one `HKSampleQuery` for lab-result records, parses the
returned FHIR JSON entirely on device, and writes the results into its own local database. That
is the whole integration. There is no upload step, so there is no upload frequency. The code path
that reads clinical records contains no networking API and constructs no URL.

**What features require this information? How is the feature enabled? How is it turned off?**

One feature: the Lab notebook, which lets a person keep their lab results alongside the rest of
their own health data and see a value's history over time.

It is enabled by an explicit, one-time user action. The user opens Log → Lab notebook → "Import
from Health", and taps a button. That tap is the only thing in the entire app that calls the
clinical-records API. There is no background delivery for clinical records, no observer, no
scheduled task, and no import at launch or on sync — a user who never opens that screen never
triggers a clinical read at all.

It is turned off in two independent ways, either of which is sufficient:

1. In iOS Settings → Privacy & Security → Health → BADAN, the user can revoke clinical-records
   access. The app then receives nothing.
2. In BADAN, the user can delete imported results individually, or turn off "Sensitive records" in
   Settings → Privacy & Security, which permanently deletes the entire encrypted database those
   records live in.

Because the app only ever reads on an explicit tap, "off" is also simply the state of not tapping.

**How else is the information utilized?**

It is not. Imported lab results are displayed in the Lab notebook and nowhere else. Specifically:

- They are **not** sent to BADAN's optional AI coach feature. The component that assembles context
  for that feature is constructed so that it can only read the app's non-sensitive database; it
  has no initializer that could bind it to the database lab results live in. This is covered by an
  automated test that seeds sensitive records and asserts none of them can appear in coach context.
- They are **not** included in a normal data export. Lab data is classified sensitive in the app's
  metric registry and is excluded from export scope unless the user explicitly selects it.
- They are **not** used to compute any score, and BADAN adds no interpretation to them. An imported
  result keeps the provider's own reference range and the provider's own abnormal flag; the app
  displays those and adds no verdict, diagnosis, or recommendation of its own.
- They are **not** used for analytics. The app contains no analytics SDK.

**Where is the information stored? Who has access to it?**

On the device only, in `badan_sensitive.db` — a separate SQLite database encrypted at rest with
SQLCipher, keyed from the device Keychain with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`,
so the key never leaves the device and is not included in backups or transferred to another
device.

Access is limited to the person using the device. There is no account, no login, no sync, and no
server-side copy — BADAN operates with no backend for health data at all. The developer has no
means of accessing a user's lab results, because they exist only inside that user's device.

Three optional, off-by-default features can reach the network. **None of them can access this
database**, and none of them can access any health record:

- an **AI coach** that sends a question the user typed;
- **delivering an export file** to an address the user entered;
- **methodology feedback** (new in build 5, described below).

All three are described in the privacy policy at https://badan.binjamshid.com/privacy.html.

## Guideline 3.1.2(c) — required subscription information

Fixed in build 1.1 (5). The purchase screen (Settings → BADAN Pro) now shows, in one view:

- **Title** of each subscription, from StoreKit's `displayName`.
- **Length**, rendered from the product's own `subscriptionPeriod` (e.g. "/ month", "/ year") so it
  is correct regardless of how a product is named.
- **Price**, from StoreKit's localized `displayPrice`, per storefront.
- **A functional link to the Terms of Use (EULA)** — https://badan.binjamshid.com/eula.html
- **A functional link to the Privacy Policy** — https://badan.binjamshid.com/privacy.html
- The renewal disclosure ("Subscriptions renew automatically until cancelled, and can be managed in
  your Apple ID settings").

The EULA link was the item cited. The privacy policy link is on the same required list and was also
missing, so both were added rather than only the one flagged. Both links open the same documents
that the App Store Connect Privacy Policy and EULA fields point to.

A screen recording of the purchase screen showing both links opening is attached.

## Also in build 1.1 (5)

Build 5 contains user-facing work completed since build 4: per-metric show/hide and pinning,
importing Apple Health history older than 90 days, a control to recompute scores, a choice of
calculation method for two derived metrics, and an on-device option that lets a user tell the app
when a calculated number did not match how they felt. None of these change how clinical records are
accessed, stored or shared.

**One of them is new and does send data, so we are declaring it rather than leaving it to be
found.** Because a user can now tell the app "this number didn't match how I felt", build 5 adds an
optional way to contribute that judgement — and nothing else — back to the developer, so the app's
calculation constants can eventually be checked against real experience instead of remaining
guesses.

It is **off unless the user turns it on**, and the switch is not even offered until they have used
the feedback feature, so nobody is asked to consent to something they have no concept of. Our App
Privacy declaration has been updated to Other Usage Data (not linked to identity, not used for
tracking) to cover it.

What a submission contains, in full: which metric and which calculation method the user disagreed
with, whether they felt better or worse than the number said, roughly how many times as a range
("10–19"), and whether the app had adjusted that number from their earlier answers.

What it never contains: any reading or health value, any magnitude, any date, any location, and any
identifier of the user or the device. Nothing is sent at all until a user has answered about the
same metric at least ten times, and submission happens at a random point 24–72 hours later so the
timing itself reveals nothing.

The user can read every submission the app has made, verbatim, in Settings → Privacy & Security.
Clinical records, lab results, and everything else in the encrypted sensitive database are
structurally excluded — the payload has no field capable of carrying a health value, and an
automated test builds a payload from known readings and fails if any of them appear in it.

## Notes to include in App Review Information for future submissions

BADAN reads HealthKit Clinical Records (lab results only, read-only) exclusively when the user taps
"Import from Health" in Log → Lab notebook. Records are parsed on device and stored in a
SQLCipher-encrypted local database. They are never uploaded, never sent to the app's optional AI
coach, never included in a default export, and never used to compute a score. The app has no
account system and no server-side storage of health data.
