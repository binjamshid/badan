### 🟠 [High] "Pause predictions" toggle does not pause the next-cycle forecast (only phase-conditioned baseline recompute)

_slice: `apps/ios/Sources/Features/Cycle`_

- **Plain language:** In the Cycle settings screen there is a switch labeled "Pause predictions" whose description tells the user it will stop next-cycle forecasts. In reality the app keeps generating and showing the next-cycle estimate range on the home and history screens after this switch is on — only a hidden background comparison feature is actually paused. Someone who turns predictions off (for privacy, accuracy, or emotional reasons in a sensitive reproductive-health module) still sees the forecast they asked to stop.
- **Impact / effort / ROI:** User-facing impact: a sensitive-module control's headline function is non-functional with no workaround, and its own copy actively misleads. Effort: small — gate the forecast on the flag (either in refreshAll step 2 or at display), or correct the copy. ROI: high — small change removes a trust-breaking broken setting.
- **Evidence:** `apps/ios/Sources/Features/Cycle/CycleConsentScreen.swift:290`; `apps/ios/Sources/Features/Cycle/CycleConsentScreen.swift:291`; `apps/ios/Sources/Features/Cycle/CycleConsentScreen.swift:173`; `apps/ios/Sources/Features/Cycle/CycleConsentScreen.swift:178`; `apps/ios/Sources/Features/Cycle/CycleConsentScreen.swift:264`; `apps/ios/Sources/Features/Cycle/CycleModuleServices.swift:116`; `apps/ios/Sources/Features/Cycle/CycleModuleServices.swift:102`; `apps/ios/Sources/Features/Cycle/CycleModuleServices.swift:106`; `apps/ios/Sources/Domain/Cycle/CyclePredictionEngine.swift:147`; `apps/ios/Sources/Domain/Cycle/CyclePredictionEngine.swift:154`; `apps/ios/Sources/Domain/Cycle/CyclePredictionEngine.swift:220`; `apps/ios/Sources/Features/Cycle/CycleHomeScreen.swift:389`; `apps/ios/Sources/Features/Cycle/CycleHistoryScreen.swift:351`; `apps/ios/Tests/CycleModuleServicesTests.swift:147`; `apps/ios/Tests/CycleModuleServicesTests.swift:162`
- **Risk if unaddressed:** A user in a sensitive reproductive-health context explicitly asks the app to stop forecasting their next cycle, and the app keeps surfacing an active predicted range on Home and History. This is a trust/feature-completeness failure and undercuts a pause capability the reproductive threat model treats as a core mitigation. It also silently makes the onboarding promise ("pause forecasts without losing your history", CycleConsentScreen.swift:264-266) false.
- **Fix direction:** Make the forecast honor env.profile.cyclePredictionsPaused. Preferred: in CycleModuleServices.refreshAll step 2, when cyclePredictionsPaused is true, emit a prediction with status == .paused (so CyclePredictionPresentation.hasRange returns false and the calm paused descriptor shows) instead of an active range; and/or have CycleHomeScreen.predictionBody / CycleHistoryScreen.predictionBody suppress the range when the flag is set. Alternatively, if pausing the forecast is genuinely out of scope, rewrite pausePredictionsSubtitle (and the pointHidePauseDelete onboarding line) so they no longer claim to pause the next-cycle forecast. The honest, user-expected fix is the former.
- **How to verify:** Enable the module and log 2+ completed cycles so an active next-cycle range renders on CycleHomeScreen and CycleHistoryScreen. Turn on "Pause predictions," then trigger a refreshAll (log a flow entry) and revisit Home/History. Expected after fix: no predicted range is shown (paused descriptor instead). Current behavior: the active range still displays. Add a unit test asserting that with cyclePredictionsPaused == true, refreshAll's appended prediction has status == .paused (mirroring testRefreshAllSkipsPhaseConditionedBaselineRecomputeWhenPredictionsPaused, which currently only covers phase baselines).


### 🟡 [Medium] In-app "Run now" silently drops the sinceLastRun fallback notice, so a delta template exports 30 days with no disclosure

_slice: `apps/ios/Sources/Features/Export/`_

- **Plain language:** If you save an export template set to "only what's new since the last run" and then tap Run on it inside the app, BADAN actually exports the last 30 days instead of just the new records — and never tells you. The exact same template run from a Shortcut DOES tell you. The app spent a lot of code computing that honesty message and then throws it away on the in-app button, which contradicts the app's whole "nothing fails silently" promise.

### 🟡 [Medium] Every SQLite read materializes a per-row [String:SQLValue] dictionary; the zero-allocation positional reader (PERF-102) has zero adopters

_slice: `Performance — SQLite read path, view-model threading, export memory, formatter/observation granularity`_

- **Plain language:** The database layer has two ways to read rows: a slow one that builds a labeled dictionary for every single row, and a fast one that skips that. The team built the fast one specifically for the heavy screens, but no part of the app actually uses it — all 149 database reads go through the slow path. On a user with a long health history this means a lot of wasted memory churn and CPU every time a screen loads or an export runs.
- **Impact / effort / ROI:** Impact: wasted allocations/CPU that scale with history size on Body's multi-family fan-out, full-history exports, background score derivation, and the main-actor firstFact() lookup. Effort: low-moderate — mechanically convert the ~5 hottest readers (rawSamples/intervalRecords/sessions/latestDerivedSeries/liveEntries) to the existing query(map:) API. ROI: high — the fast path already exists and is unit-testable.
- **Evidence:** `apps/ios/Sources/Storage/SQLite/SQLiteConnection.swift:103`; `apps/ios/Sources/Storage/SQLite/SQLiteConnection.swift:117`; `apps/ios/Sources/Storage/SQLite/SQLiteConnection.swift:126`; `apps/ios/Sources/Storage/SQLite/SQLiteConnection.swift:129`; `apps/ios/Sources/Storage/SQLite/SQLValue.swift:20`; `apps/ios/Sources/Storage/SQLite/SQLValue.swift:23`; `apps/ios/Sources/Storage/Repositories/MeasurementRepository.swift:71`; `apps/ios/Sources/Storage/Repositories/MeasurementRepository.swift:111`; `apps/ios/Sources/Storage/Repositories/MeasurementRepository.swift:324`; `apps/ios/Sources/Storage/Repositories/DerivationRepository.swift:72`; `apps/ios/Sources/Storage/Repositories/DerivationRepository.swift:120`
- **Risk if unaddressed:** Left unaddressed, load/derivation/export times degrade proportionally to a user's stored history. Per row the app pays: one Dictionary allocation, one boxed SQLValue enum per column (each .text boxes a fresh String), N string-key hashes to insert, then N more string-key hashes when the readXXX decoder looks each column back up by name. For a raw-sample table with 100k+ rows this is 100k dictionaries and millions of hash operations per read — cost that lands on background BGProcessing time budgets (which iOS caps) and on the main-actor firstFact() path.
- **Fix direction:** Adopt the existing positional SQLiteConnection.query<T>(map:) (SQLiteConnection.swift:129) in the hot readers. Read columns by integer index off the raw statement inside the map closure (as the API's own PERF-102 doc describes) instead of `db.query(sql,params).map(Self.readXXX)` which routes through the dictionary builder. Prioritize rawSamples, intervalRecords, sessions, latestDerivedSeries, and hydration.liveEntries — the readers behind Body's fan-out, Timeline assembly, and the export gather.
- **How to verify:** Add/extend a case in apps/ios/Tests/ViewModelPerformanceTests.swift that seeds a large store (e.g. 50k+ raw samples for one metric) and measures rawSamples() wall time + allocations with XCTMemoryMetric/XCTClockMetric, before vs after migrating that reader to query(map:). Confirm a measurable allocation drop and no behavioral change against existing repository tests. Cross-check with an Instruments Allocations run while loading Body / running a full export.


### ⚪ [Low] JSON export builds the entire bundle in a single in-memory Data, and sensitive-export encryption re-reads every file fully into memory (CSV was streamed, JSON was not)

_slice: `Performance — SQLite read path, view-model threading, export memory, formatter/observation granularity`_

ROI: moderate — real only for large histories, and the export already runs off the main actor so there is no UI-jank component.
- **Evidence:** `apps/ios/Sources/Export/ExportRunner.swift:732`; `apps/ios/Sources/Export/ExportRunner.swift:741`; `apps/ios/Sources/Export/ExportRunner.swift:413`; `apps/ios/Sources/Export/ExportRunner.swift:416`; `apps/ios/Sources/Export/ExportRunner.swift:594`; `apps/ios/Sources/Export/ExportRunner.swift:186`; `apps/ios/Sources/Export/JSONBundleWriter.swift:154`; `apps/ios/Sources/Features/Export/ExportManageService.swift:235`
