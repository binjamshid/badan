# Badan technical blueprint

Badan's iOS and Android apps do ingestion, storage, score computation and export generation on the device. The apps use shared data contracts in native code. A separate API supports optional iOS connected features. See [the development guide](DEVELOPMENT.md) for the local sample-data workflow.

## Trace a synthetic resting heart rate

This example uses a fictional **63 bpm** reading. It illustrates the same canonical path on each platform with one source and an already established personal baseline.

1. **Read.** The sample health stores can emit an interval DTO for `heart.rhr`. A connected iOS app maps HealthKit's resting heart rate aggregate to the same metric. A connected Android app maps Health Connect's `RestingHeartRateRecord` to an interval. The source-specific aggregation marker can differ, while the metric and unit agree. [iOS type map](../apps/ios/Sources/Platform/Health/HKTypeMap.swift), [Android type map](../apps/android/app/src/main/java/net/albayyan/badan/platform/health/HcTypeMap.kt)
2. **Normalize and store.** The ingestion pipeline asks `MetricRegistry` for the canonical unit, normalizes the supplied value and writes an `IntervalRecord` through `MeasurementRepository`. Here 63 bpm stays 63 bpm. The row keeps the time bounds, time zone, source and source record identity where available. Local-day grouping uses that time-zone context. [iOS ingestion](../apps/ios/Sources/Domain/Ingestion/IngestionPipeline.swift), [Android ingestion](../apps/android/app/src/main/java/net/albayyan/badan/domain/ingestion/IngestionPipeline.kt)
3. **Derive.** `DerivationCoordinator` refreshes personal baselines and computes effort and sleep outputs before Readiness. `ReadinessEngine` selects the day's eligible interval and standardizes it against the user's resting-heart-rate baseline. Suppose 63 bpm is one robust standard deviation above the baseline. Under the default 2.0.0 method the resting-heart-rate sub-score is 30. If sleep performance is 80 and HRV and respiratory rate are unavailable, the two present weights are equal after renormalization and the illustrative composite is 55. This is a reduced-input estimate, with a confidence ceiling of 0.4 before any maturity or context adjustment. The example assumes the default method and no personal score offset. [Baselines](algorithms/baselines.md), [Readiness methodology](algorithms/readiness.md), [iOS coordinator](../apps/ios/Sources/Domain/Derivation/DerivationCoordinator.swift), [Android coordinator](../apps/android/app/src/main/java/net/albayyan/badan/domain/derivation/DerivationCoordinator.kt)
4. **Persist and explain.** The derived row has metric ID `readiness.score`, a local-day period key, confidence, a provisional flag, and algorithm ID and version. Its `InputManifest` records the contributing record IDs and their contributions, including the resting-heart-rate interval and the sleep performance value. The score's anatomy view can explain those inputs. Recomputations that publish a new result append a row so prior results retain their original calculation identity. [iOS Readiness engine](../apps/ios/Sources/Domain/Derivation/ReadinessEngine.swift), [Android Readiness engine](../apps/android/app/src/main/java/net/albayyan/badan/domain/derivation/ReadinessEngine.kt)
5. **Export.** With the two metric IDs and their date range in scope and both measured and derived data selected, `ExportRunner` can write the interval to `raw.csv` and the score to `derived.csv`. A CSV export includes a manifest with schema version and SHA-256 checksums. JSON uses distinct measured and derived sections within a bundle. [iOS ExportRunner](../apps/ios/Sources/Export/ExportRunner.swift), [Android ExportRunner](../apps/android/app/src/main/java/net/albayyan/badan/export/ExportRunner.kt), [generated data dictionary](../DATA_DICTIONARY.md)

## Shared sources and generated mirrors

| Files to edit | Where the apps consume them |
| --- | --- |
| [Metric registry](../packages/metric-ontology/registry.json), [algorithm parameters](../packages/contracts/algorithms/algorithms.json), [sensor-quality rules](../packages/contracts/sensor_quality.json), shared insight and dictionary files | iOS `Sources/Resources/` and Android `app/src/main/assets/`. Android also mirrors algorithm parameters into `app/src/main/resources/` for JVM classpath loading. |
| [CSV columns](../packages/export-schemas/csv_columns.json), [JSON bundle schema](../packages/export-schemas/json_bundle.schema.json) | The CSV contract is mirrored into both apps. Native writers emit the JSON bundle, which CI checks against the canonical schema with fixture instances. The data dictionary is generated from the export contracts and registry. |
| [iOS-specific dictionaries and telemetry schema](../scripts/sync_ios_resources.sh) | The iOS sync script also copies activity, movement and lab vocabularies and the methodology telemetry schema. The API applies the telemetry contract through its request models. |
| [Shared conformance fixtures](../packages/fixtures/) | Selected Swift and Kotlin tests read the same artifacts from the repository to check units, exports and other contract behavior. |

Author contract changes in `packages/`, regenerate resource copies with the [iOS sync script](../scripts/sync_ios_resources.sh) and [Android sync script](../scripts/sync_android_assets.sh), and review the generated changes. When changing score semantics or parameters, update the algorithm contract and version, the methodology and the focused expectations on both platforms. Retain the identifiers and versions on old derived rows so an existing score remains explainable. [Algorithm methodology](algorithms/README.md), [export-schema changelog](export-schema-changelog.md)

## Platform scope and parity

| State in this source tree | Examples |
| --- | --- |
| Implemented on both phone platforms | Sample-data mode, native health-source ingestion, personal baselines and Readiness, local log entry and scoped export. |
| Platform-specific implementation | iOS maps HealthKit SDNN to `heart.hrv` in milliseconds. Android maps Health Connect RMSSD to the same ID and unit. SDNN and RMSSD measure different properties. Both feed each platform's HRV term in Readiness where usable, so matching IDs alone do not make readings or scores comparable. Apple widgets and the watch app have implemented snapshot consumers. [iOS type map](../apps/ios/Sources/Platform/Health/HKTypeMap.swift), [Android type map](../apps/android/app/src/main/java/net/albayyan/badan/platform/health/HcTypeMap.kt) |
| Implemented on iOS with separate setup | App Attest-backed coach, Apple sign-in and account/referral flows, methodology telemetry with consent. The account API retains compatibility with entitlement reports from older app releases. Current clients apply no purchase-based restrictions. [Account ADR](adr/ADR-0014-accounts-and-cross-platform-entitlement.md), [API entry point](../backend/api/main.py) |
| Provisional methodology | The default Readiness method has published parameters and a provisional status. See [its methodology](algorithms/readiness.md) for input, maturity and confidence rules. |
| Scaffold or gated | Android `:wear` establishes the module boundary and may depend on `:contracts`, the pure Kotlin wire contract. The tracked Wear module is a scaffold for a phone-snapshot renderer. The REST export deliverer is disabled in both app compositions. [Wear module](../apps/android/wear/src/main/java/net/albayyan/badan/wear/WearModule.kt), [iOS REST gate](../apps/ios/Sources/Export/Destinations/RESTDestinationAvailability.swift), [Android REST gate](../apps/android/app/src/main/java/net/albayyan/badan/export/destinations/RestDestinationAvailability.kt) |

The [canonicalization fixtures](../packages/fixtures/canonicalization/README.md) check unit conversions and adapter mappings on both platforms. The [export fixtures](../packages/fixtures/export/README.md) check exact bytes for fixed inputs and scope. Both native CI jobs depend on a contract job that checks selected resource mirrors, fixture hashes, the generated dictionary and the export schema. Verify the iOS activity, movement and lab mirrors separately. The Android `AlgorithmResourceMirrorTest` checks the algorithm classpath copy. Use each fixture's stated scope when evaluating parity. Device permissions, storage, background delivery and paired watch behavior need their own runtime checks. [.github/workflows/ci.yml](../.github/workflows/ci.yml), [Android algorithm mirror test](../apps/android/app/src/test/java/net/albayyan/badan/AlgorithmResourceMirrorTest.kt)
